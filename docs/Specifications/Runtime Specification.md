# Runtime & Concurrency

Спецификация описывает, как приложение живёт внутри long-running PHP-рантаймов: 
**Swoole / OpenSwoole**, **RoadRunner**, **FrankenPHP (worker mode)**, а также 
Fiber-based рантаймов (Amp, ReactPHP, Revolt).

Спецификация разделена на **ядро** (обязательно для любого рантайма) и 
**опциональные профили** (включаются по возможностям рантайма).

---

## 1. Термины

| Термин                  | Определение                                                                                                    |
|-------------------------|----------------------------------------------------------------------------------------------------------------|
| **Runtime**             | Среда выполнения: Swoole, RoadRunner, FrankenPHP, FPM и т.д.                                                   |
| **Server / Supervisor** | Процесс, который запускает воркеры и управляет ими (Swoole master, Go-сервер RoadRunner, Caddy во FrankenPHP). |
| **Worker**              | Единица исполнения PHP-кода: процесс или поток.                                                                |
| **Application**         | Загруженное приложение (контейнер, конфиг, роутер). Живёт столько же, сколько воркер.                          |
| **Request**             | Обработка одного входящего запроса (HTTP, gRPC, job, WebSocket-сообщение).                                     |
| **Coroutine / Fiber**   | Единица конкурентности внутри воркера. Есть не во всех рантаймах.                                              |
| **Concurrency**         | Несколько задач выполняются вперемешку **внутри** одного воркера.                                              |
| **Parallelism**         | Несколько задач выполняются одновременно в **разных** воркерах.                                                |

---

## 2. Модель вложенности

```
+------------------------------------------------------------------+
| Server / Supervisor Lifecycle                                    |
| +----------------------------------------------------------------+
| | Worker Lifecycle (процесс или поток)                           |
| | +--------------------------------------------------------------+
| | | Application Lifecycle (один на воркер)                       |
| | | +------------------------------------------------------------+
| | | | Request Lifecycle                                          |
| | | | +----------------------------------------------------------+
| | | | | Coroutine Lifecycle (опционально, профиль "coroutines")  |
| | | | +----------------------------------------------------------+
| | | +------------------------------------------------------------+
| | +--------------------------------------------------------------+
| +----------------------------------------------------------------+
+------------------------------------------------------------------+
```

Правило: **ресурс не должен жить дольше своего владельца и не должен 
быть доступен тем, кто живёт меньше него без явной передачи**.

---

## 3. Runtime Capabilities

Рантайм объявляет свои возможности. Остальные части спецификации опираются 
на них, а не на название рантайма.

```php
interface RuntimeCapabilities
{
    public function concurrentRequestsPerWorker(): bool; // несколько запросов одновременно в одном воркере
    public function coroutines(): bool;                  // есть корутины/файберы на уровне PHP
    public function threads(): bool;                     // воркеры - потоки (ZTS), а не процессы
    public function asyncIo(): AsyncIoMode;              // None | Fibers | Coroutines
    public function requiresConnectionPool(): bool;      // соединение нельзя делить между запросами
    public function supportsBackgroundTasks(): bool;
    public function supportsStreaming(): bool;           // SSE / chunked / WebSocket
    public function supportsHotReload(): bool;
}

enum AsyncIOMode { case None; case Fibers; case Coroutines; }
```

### Матрица рантаймов

| Capability                    | Swoole / OpenSwoole | RoadRunner                     | FrankenPHP (worker) | FPM (для сравнения)            |
|-------------------------------|---------------------|--------------------------------|---------------------|--------------------------------|
| Воркер                        | процесс             | процесс                        | поток (ZTS)         | процесс                        |
| `concurrentRequestsPerWorker` | да                  | нет                            | нет                 | нет                            |
| `coroutines`                  | да (встроенные)     | нет                            | нет                 | нет                            |
| `threads`                     | нет (по умолчанию)  | нет                            | да                  | нет                            |
| `asyncIo`                     | Coroutines          | None (или Fibers через Revolt) | None (или Fibers)   | None                           |
| `requiresConnectionPool`      | да                  | нет                            | нет                 | нет                            |
| Application                   | один на процесс     | один на процесс                | один на поток       | пересоздаётся на каждый запрос |

## 4. Ядро (обязательно для всех рантаймов)

### 4.1 Server / Supervisor Lifecycle

Управление воркерами снаружи PHP.

- Запуск и остановка воркеров.
- Обработка сигналов (`SIGTERM`, `SIGHUP`, `SIGUSR1`).
- **Graceful shutdown**: перестать принимать новые запросы, дождаться текущих, 
закрыть ресурсы.
- Hot reload (если поддерживается): замена воркеров без потери запросов.
- Healthcheck и метрики.

### 4.2 Worker Lifecycle

Управление жизнью воркера.

| Этап       | Что происходит                                                                  |
|------------|---------------------------------------------------------------------------------|
| `boot`     | Загрузка кода, создание Application, прогрев                                    |
| `ready`    | Воркер принимает запросы                                                        |
| `recycle`  | Плановый перезапуск по лимиту (`max_requests`, `max_jobs`, `ttl`, порог памяти) |
| `shutdown` | Graceful остановка: закрытие соединений, flush буферов                          |
| `crash`    | Аварийное завершение: fatal error, OOM, `exit()`                                |

Обязанности:

- Перезапуск воркера по лимитам для защиты от утечек памяти.
- Закрытие всех ресурсов уровня Worker и Application при остановке.
- Обработка `exit` / `die` и fatal errors, чтобы они не роняли 
соседние запросы (где возможно).
- Корректное поведение при падении воркера: запрос получает ошибку, 
воркер заменяется новым.

### 4.3 Application Lifecycle

- Application создаётся **один раз на воркер** и разделяется между запросами.
- Содержит только **stateless** или **безопасно разделяемые** сервисы: конфиг, 
роутер, скомпилированный контейнер, кеши метаданных.
- В процессах и потоках статика и общая память ведут себя по-разному. 
В ZTS-рантаймах (FrankenPHP) каждый поток имеет собственный экземпляр 
Application.

### 4.4 Request Lifecycle

Главная задача любого long-running рантайма: **изолировать запрос при общем 
Application**.

Этапы:
1. `begin`: создать RequestContext, инициализировать request-scoped сервисы.
2. `handle`: выполнить обработку.
3. `terminate`: отправить ответ, выполнить отложенные действия.
4. `reset`: сбросить состояние (см. 4.5).
5. `end`: освободить ресурсы запроса.

Гарантии:
- Данные одного запроса недоступны другому.
- Исключение в запросе не ломает воркер.
- Ресурсы запроса освобождаются в `finally`, даже при ошибке.

### 4.5 State Reset

Обязательный механизм очистки между запросами. Для рантаймов без корутин 
это самая важная часть изоляции.

Что сбрасывается:
- Request-scoped сервисы контейнера (аналог `kernel.reset` в Symfony, 
`ResetInterface`).
- Статические свойства и синглтоны с состоянием.
- Суперглобалы (`$_GET`, `$_POST`, `$_SERVER`, `$_COOKIE`, `$_FILES`, 
`$_SESSION`).
- Буферы вывода, заголовки, `http_response_code`.
- Состояние сессии, аутентификации, локали, часового пояса.
- Логгеры и контексты трассировки (correlation id).
- Открытые транзакции БД (rollback, если остались).

```php
interface Resettable
{
    public function reset(): void;
}
```

### 4.6 Resource Lifecycle

Ресурсы классифицируются по времени жизни.

| Scope           | Время жизни         | Примеры                                               |
|-----------------|---------------------|-------------------------------------------------------|
| **Server**      | Весь сервер         | Общая память, таблицы Swoole, метрики                 |
| **Worker**      | Один воркер         | Соединения воркера, пул, кеш в памяти                 |
| **Application** | Воркер (после boot) | Контейнер, конфиг, роутер                             |
| **Request**     | Один запрос         | RequestContext, UoW, транзакция, текущий пользователь |
| **Coroutine**   | Одна корутина       | Локальные данные корутины, дочерние задачи            |

Правила:
- Ресурс создаётся в том scope, где он нужен, и закрывается при выходе из него.
- Ресурс более узкого scope нельзя хранить в более широком (запросный объект в синглтоне).
- Для каждого ресурса определено, кто его владелец и кто закрывает.

### 4.7 Execution Context

Контейнер для данных текущего исполнения (запроса, а при наличии корутин 
и корутины).

```php
interface ExecutionContext
{
    public function get(string $key, mixed $default = null): mixed;
    public function set(string $key, mixed $value): void;
    public function has(string $key): bool;
    public function parent(): ?ExecutionContext;
}
```

Привязка контекста зависит от рантайма:

| Рантайм                   | Где хранится текущий контекст                        |
|---------------------------|------------------------------------------------------|
| Swoole                    | `Swoole\Coroutine::getContext()` (контекст корутины) |
| Fiber-based (Amp, Revolt) | `FiberLocal` / контекст файбера                      |
| RoadRunner                | Свойство воркера, пересоздаётся на каждый запрос     |
| FrankenPHP                | Свойство потока, пересоздаётся на каждый запрос      |

Поведение:
- В рантаймах с `concurrentRequestsPerWorker = false` контекст может быть простым хранилищем, живущим до `reset`.
- В рантаймах с корутинами контекст **обязан** быть привязан к корутине. Глобальные и статические переменные для данных запроса запрещены.
- Дочерняя корутина наследует контекст родителя явно (копирование или ссылка на parent), а не неявно.

### 4.8 Database & Connections (ядро)

Контракт для любых рантаймов:
- Соединение **не делится** между одновременно исполняющимися запросами.
- Состояние соединения (транзакция, `SET`-переменные, prepared statements, выбранная БД) очищается или проверяется перед возвратом в обращение.
- Долгоживущие соединения проверяются на живость (ping, reconnect по таймауту).
- Транзакция не может пережить запрос: незавершённая транзакция откатывается в `reset`.

## 5. Опциональные профили

Профиль активируется, только если рантайм объявляет соответствующую capability. 
В остальных случаях он не используется и не должен навязываться.

### 5.1 Профиль `coroutines`

*Активируется при `coroutines = true` (Swoole, Fiber-based рантаймы).*

#### Coroutine Runtime

- Создание, ожидание и отмена корутин.
- Структурированная конкурентность: родитель дожидается детей или явно отменяет их.
- **Cancellation и timeout** для корутин и операций ввода-вывода.
- Обработка исключений в дочерних корутинах (не теряются молча).
- Лимит числа одновременных корутин (backpressure).

#### Coroutine Lifecycle

| Этап                         | Описание                              |
|------------------------------|---------------------------------------|
| `spawn`                      | Создание, наследование контекста      |
| `run`                        | Выполнение                            |
| `suspend`                    | Ожидание I/O или другой корутины      |
| `finish` / `cancel` / `fail` | Завершение, отмена или ошибка         |
| `cleanup`                    | Освобождение ресурсов уровня корутины |

#### Connection Pool

Нужен при `requiresConnectionPool = true`: параллельные корутины не могут делить одно соединение.
- Пулы для MySQL, PostgreSQL, Redis, HTTP-клиентов и др.
- Параметры: `min`, `max`, `acquireTimeout`, `idleTimeout`, `maxLifetime`.
- Каждый пул принадлежит воркеру (не передаётся между процессами).
- Соединение берётся из пула на время запроса или операции и **обязательно** возвращается (`try/finally`).
- Соединение внутри транзакции привязано к одному контексту до `commit` / `rollback`.
- Поведение при исчерпании пула: ожидание с таймаутом, затем ошибка.

#### Coroutine-safe Database

- Database Layer не хранит состояние запроса в свойствах общих объектов.
- Текущее соединение и транзакция определяются из `ExecutionContext`.
- Вложенные транзакции и savepoints изолированы между корутинами.
- Для Swoole драйверы либо работают через хуки (`SWOOLE_HOOK_ALL`), либо 
используют специализированные корутинные клиенты.

### 5.2 Профиль `threads`

*Активируется при `threads = true` (FrankenPHP).*

- Каждый поток имеет собственное окружение PHP; статические переменные 
и состояние **не разделяются** между потоками.
- Общая память и межпоточное взаимодействие выполняются только через явные механизмы рантайма.
- Расширения PHP должны быть thread-safe.
- Число потоков и лимиты ресурсов задаются на уровне сервера.

### 5.3 Профиль `background`

*Активируется при `supportsBackgroundTasks = true`.*

- Фоновые задачи: task workers (Swoole), jobs/queues (RoadRunner), 
отдельные воркеры (FrankenPHP).
- Фоновая задача имеет собственный Execution Context и Resource Lifecycle,
она не наследует запросный контекст.
- Отложенные действия после ответа (`terminate`) не должны зависеть от 
закрытых ресурсов запроса.

### 5.4 Профиль `streaming`

*Активируется при `supportsStreaming = true`.*

- SSE, WebSocket, chunked-ответы, долгие соединения.
- Время жизни соединения может превышать обычный Request Lifecycle. Для него определён собственный scope и правила очистки.
- Обработка обрыва соединения клиентом и отмена связанных операций.

## 6. Async I/O

Единый интерфейс **не гарантирует единую семантику**. Он гарантирует единый способ вызова, а реальное поведение зависит от `asyncIo`.

```php
interface AsyncIO
{
    public function mode(): AsyncIoMode;
    public function run(callable $task): Future;      // Future можно ждать синхронно
    public function all(array $tasks): array;
    public function sleep(float $seconds): void;
    public function timeout(float $seconds, callable $task): mixed;
}
```

| `asyncIo`    | Поведение `run()` / `all()`                                                                                    |
|--------------|----------------------------------------------------------------------------------------------------------------|
| `Coroutines` | Задачи реально выполняются конкурентно в корутинах, I/O не блокирует воркер                                    |
| `Fibers`     | Конкурентность поверх Fibers и event loop (Revolt/Amp/ReactPHP). Блокирующие вызовы блокируют loop             |
| `None`       | Задачи выполняются **последовательно** и синхронно. Это корректный фасад, но без выигрыша в производительности |

Требования:

- Код, использующий `AsyncIo`, должен быть корректен при любом режиме. Он не может полагаться на фактическую параллельность.
- Выигрыш от конкурентности для режима `None` достигается числом воркеров, а не внутри запроса.
- Блокирующие вызовы (`sleep`, синхронный `curl`, `file_get_contents`) в режимах с event loop считаются ошибкой.

## 7. Обработка ошибок и аварийных ситуаций

| Ситуация                             | Требуемое поведение                                                |
|--------------------------------------|--------------------------------------------------------------------|
| Необработанное исключение в запросе  | Логирование, ответ 500, `reset`, воркер продолжает работу          |
| Fatal error / OOM                    | Воркер завершается и заменяется, запрос получает ошибку            |
| `exit()` / `die()` в коде приложения | Перехватывается или приводит к контролируемому перезапуску воркера |
| Исключение в дочерней корутине       | Передаётся родителю или логируется, не теряется                    |
| Потеря соединения с БД / Redis       | Reconnect или удаление соединения из пула, ошибка запросу          |
| Таймаут запроса                      | Отмена связанных операций, освобождение ресурсов                   |
| Утечка памяти                        | Перезапуск воркера по лимиту памяти или числа запросов             |

## 8. Чек-лист совместимости рантайма

Приложение считается совместимым с рантаймом, если:
- [ ] Application не хранит запросное состояние в синглтонах и статике.
- [ ] Реализован `reset` между запросами.
- [ ] Суперглобалы и вывод очищаются после каждого запроса.
- [ ] Ресурсы закрываются по scope и освобождаются в `finally`.
- [ ] Соединения не делятся между одновременными запросами.
- [ ] Graceful shutdown закрывает все ресурсы воркера.
- [ ] Воркер перезапускается по лимитам памяти или запросов.
- [ ] Код не полагается на реальную параллельность `AsyncIo`.
- [ ] Для рантаймов с корутинами используется `ExecutionContext`, привязанный к корутине.
- [ ] Для рантаймов с потоками проверена thread-safety расширений.

## 9. Профили по рантаймам (кратко)

| Рантайм                     | Ядро | Профили                                     |
|-----------------------------|------|---------------------------------------------|
| **Swoole / OpenSwoole**     | да   | `coroutines`, `background`, `streaming`     |
| **RoadRunner**              | да   | `background` (jobs), `streaming` (частично) |
| **FrankenPHP**              | да   | `threads`, `streaming` (SSE), `background`  |
| **Amp / ReactPHP / Revolt** | да   | `coroutines` (на Fibers), `streaming`       |

Режимы запуска рантайма:
- sync — обычное последовательное исполнение.
- coroutines — конкурентное исполнение через корутины.
- threads — многопоточное исполнение.
- background — фоновые задачи.
- streaming — потоковая передача.

## Реализация в Neo (Swoole / OpenSwoole)

Модуль: `neo/Foundation/Runtime`. Синхронный PHP остаётся режимом по умолчанию: `public/index.php` не меняется, рантайм определяется на лету (`Runtime::current()`), а адаптер долгоживущего сервера выбирает его явно при старте воркера.

### Что где

| Что | Где |
|---|---|
| Контракты: `RuntimeContract`, `RuntimeCapabilities`, `ExecutionContext`, `Resettable`, `AsyncIO`/`Future`, `ChannelContract` | `neo/Foundation/Runtime/` |
| Контекст в стиле Hyperf: `Context::get/set/has/destroy/getOrSet/override/inherited/copyFromParent` | `Runtime/Context.php` |
| Жизненный цикл воркера и запроса: `Lifecycle` (`workerStart`, `requestEnd`, `workerStop`) | `Runtime/Lifecycle.php` |
| Sync: `SyncRuntime`, `ProcessContext` (процесс + отдельно на Fiber), `SyncAsyncIO` (режим `None`) | `Runtime/Sync/` |
| Swoole и OpenSwoole одним адаптером: `SwooleApi` выбирает `\Swoole\*` или `\OpenSwoole\*` | `Runtime/Swoole/` |
| Универсальный пул (`Pool`, `PoolOptions`) на каналах рантайма | `Runtime/Pool/` |
| HTTP-сервер: воркер-lifecycle, один запрос = одна корутина | `neo/Network/Http/Server/SwooleServer.php` |

Запуск: `php cli serve --swoole` (настройки в `app/Config/Runtime.php`).

### Правила изоляции (что гарантирует движок)

1. Данные запроса лежат в `Context` (контекст корутины), а не в свойствах синглтонов: `RequestContext`, renderer во View, локаль `LangProcessor`.
2. Соединение БД не делится между запросами: в корутине `DatabaseManager` берёт его из пула воркера при первом обращении и возвращает в конце запроса (`Lifecycle::requestEnd` и `defer` как подстраховка). Транзакция не переживает запрос: при возврате в пул делается откат. Оборванное соединение (`isBroken`) закрывается, после простоя делается ping. Пул отключается для соединения ключом `pool.enabled = false`; sqlite `:memory:` не пулится автоматически.
3. Пулы и соединения принадлежат воркеру: на `workerStart` всё, что открыл master до fork, забывается.
4. Статическое состояние Chronos (локаль, начало недели, выходные, test-now) возвращается к снимку после каждого запроса.
5. Исключение (в корутине `exit()` тоже становится исключением) завершает только свой запрос.
6. Хуки ввода-вывода по умолчанию: всё, кроме файловых и sqlite. Файловый кэш и файловые сессии не рассчитаны на приостановку посреди операции.

### Правила для кода приложения

- Не храните данные запроса в свойствах сервисов и в `static`: используйте `Context`.
- Глобальные настройки (Chronos, `Model::preventLazyLoading`, макросы) задаются при запуске, а не на запрос.
- Сервис с собственным состоянием между запросами реализует `Resettable` и регистрируется: `$app->make(Lifecycle::class)->resettable(MyService::class)`.
- Конкурентные задачи: `Runtime::current()->async()->all([...])`. В sync-режиме те же вызовы выполняются последовательно, код остаётся корректным.
- Дочерняя корутина (`go()`) не получает данные родителя копированием: `Context::inherited()` ищет у родителя, `Context::copyFromParent()` копирует явно. Соединение БД у дочерней корутины своё.

### Как добавить другой рантайм (RoadRunner, FrankenPHP)

1. Реализовать `RuntimeContract` (профили флагов уже есть: `Capabilities::roadRunner()`, `Capabilities::frankenPhp()`).
2. Написать адаптер сервера, который на старте воркера делает `Runtime::use(...)` и `Lifecycle::workerStart()`, а после каждого запроса вызывает `Lifecycle::requestEnd()`.
3. Остальной код (`HttpKernel`, `Context`, пулы, `Resettable`) менять не нужно.

### Таймаут запроса, фоновые задачи, чистка пула

- **Таймаут запроса:** `runtime.swoole.request_timeout` (секунды). Запрос выполняется в дочерней корутине; по истечении времени она отменяется, ресурсы возвращаются в пул, клиент получает 504. Отмена срабатывает, когда запрос ждёт ввод-вывод: чистый CPU-цикл прервать нельзя.
- **Фоновые задачи:** класс реализует `Neo\Foundation\Runtime\Tasks\Task`, отправка `TaskDispatcher::dispatch(MyTask::class, ['id' => 5])` (или `Runtime::current()->tasks()`). Исполнитель выбирается рантаймом: sync выполняет сразу; Swoole без task workers запускает корутину воркера; с `runtime.swoole.task_workers > 0` задача уходит в отдельный процесс. Данные только в `$payload` (сериализуемые), замыкания не передаются.
- **Чистка пула:** `pool.reap_interval` (секунды, 0 = выключена). Таймер закрывает ресурсы, простоявшие дольше `idle_timeout`, но оставляет `min`. Останавливается вместе с пулом. В sync-рантайме таймеров нет.

### Известные ограничения

- Код `SwooleServer` и `SwooleApi` проверен на заглушках, но не на живом расширении.
- Задачи в task workers не повторяются при ошибке: сбой логируется. Ретраи и очередь с гарантиями доставки не реализованы.
