# Деплой

Деплой осуществляется автоматически с помощью Webhook с Вашего 
Git-сервиса. Он отправляет пост запрос, мы же сразу делаем 
всё необходимое.

## Схема

Вся схема деплоя автоматчиески логируется в файл `deployment.log`

```
Request Webhook Accepted.
    ↓
gil pull origin master
    ↓
Сброс общего кэша (php cli cache:clear)
    ↓
Save Миграции (php cli migrate без rename/delete)
    ↓
OPcache Clear (если включен OpCache)
    ↓
OPcache Precompile (если включен OpCache)
    ↓
Swoole Worker Restart (если включен Swoole)
    ↓
Health Check
    ↓
Application Ready
```

## Rollback

Если что-то пошло не так мы обязаны откатиться к предыдущей 
рабочей версии. Для этого мы должны перед стартом деплоя 
выгрузить всю бд в отдельный sql-дамп. Скопировать содержимое 
всей папки проекта в отдельную бэкап директорию со своим 
хэшем последнего гит-коммита (лучше всего это сделать через 
bash скрипт на UNIX чтобы не потерять файлы). Так мы получим 
полный бэкап проекта. В случае отката перенаправляем прокси 
на другую папку временную, где указываем в вебе экран технических 
работ. В этот момент создаём новую БД и грузим в неё дамп. 
Копируем бэкап папки в новую папку которая сейчас станет 
продом. В новой папке выполняем все нужное. Переключаем 
nginx на новую папку, сервер работает и успешно откатился.

## Стратегии

### Application Rollback
Если проблема только в коде:
1. Переключаем приложение на предыдущий release.
2. Перезапускаем Swoole.
3. Выполняем Health Check.
4. Возвращаем приложение в рабочее состояние.
БД не трогаем.

### Full Rollback
Если проблема затронула структуру или данные БД:
1. Включаем Maintenance Mode.
2. Останавливаем запись данных.
3. Восстанавливаем предыдущую версию БД.
4. Переключаем приложение на предыдущий release.
5. Перезапускаем Swoole.
6. Выполняем Health Check.
7. Снимаем Maintenance Mode.

## Идеи

Вместо копирования всей папки проекта
Я бы использовал структуру:
```
project/
releases/
a81f42c/
b92f51d/
c73e21a/
    shared/
        .env
        storage/
        backups/
            database/
            files/
    current -> releases/c73e21a/
```
Каждый release представляет собой самостоятельную версию приложения.

При деплое:
- Создаётся новая директория.
- Загружается конкретный Git commit.
- Подключаются shared-файлы.
- Устанавливаются зависимости.
- Выполняются проверки.
- Создаётся резервная копия БД.
- Проводятся миграции.
- Выполняется переключение current.
  Для переключения достаточно атомарно заменить символическую ссылку.

Что обязательно добавить в Deployment Manager
Возможность	Назначение
Deployment Lock	Защита от параллельных деплоев
Commit Tracking	Точный SHA развёрнутой версии
Release History	История всех релизов
Database Backup	Резервная копия БД
File Backup	Резервная копия пользовательских файлов
Auto Rollback	Автоматический возврат к предыдущему release
Maintenance Mode	Технические работы
Health Check	Проверка работоспособности
Deployment Log	Подробный журнал операций

Особенно рекомендую хранить не только deployment.log, но и отдельный JSON-отчёт каждого деплоя:

Моя главная рекомендация
Архитектурное решение
Я бы сделал Deployment самостоятельным модулем Neo, а не набором bash-команд.

Например:
Neo/
Deployment/
Webhook/
Manager/
Releases/
Backup/
Rollback/
Migrations/
Health/
Logging/


И команды:
php cli deploy:run
php cli deploy:status
php cli deploy:history
php cli deploy:rollback
php cli deploy:backup
php cli deploy:clean


deploy:clean будет удалять старые релизы, оставляя последние N версий.
