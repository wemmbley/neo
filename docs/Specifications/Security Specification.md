# Авторизация приложения

Базово приложение должно иметь роли, права и самих юзеров. 
Нужен так же волшебный сафад `auth()` с помощью которого можно быстро осуществить 
все необходимые операции и проверки в отношении пользователя.

## Зависимости

Данный модуль напрочь завязан на роутингах, мидллвэрах и маршрутизации. 
К сожалению, связность будет высокая, но нет необходимости её избегать понапрасну.
Так же нужны контроллеры и респонсы. В общем, в системе уже должен быть реализован 
`Http` модуль секции `Network`. Без него никак.

Вторая зависимость - `ORM`. Без доступа к юзеру мы не сможем никак распознать его. 
Третья зависимость - `Session`, хотя бы на БД адаптированная, иначе пользователь 
будет вечно вылетать.

## Сущности

#### User

Базовая сущность идентификации, аутентифкации и авторизации.

#### Guard

Способ проверки прав пользователя и способ его авторизации в системе. 
Бывает 3х типов из коробки: 
- `web` доступ осутвляется посредством веба, все запросы с фронта разрешены.
- `auth` - доступ разрешен только пользователям вошедшим в систему. 
- `admin` - доступ разрешен пользователям вошедшим с ролью `admin`
- `api` - дополнительный тип для тротлинга, рейтлимитинга апи и белых списков

#### Gate

Разовая проверка пользователя на право делать одно действие.

#### Policy

Специфический класс ответственный за отдельные проверки для конкретной модели. 
Это низкоуровневый слой, которые позволяет уточнить возможность выполнять 
ту или иную операцию с моделью. Используется чаще всего в контроллере. 
По сути это агрегатор гейтов в удобном классе.

#### Role

Роль выступает агретаром пермиссий. Он их группирует алиасом.
Например роль модератор может иметь сразу несколько пермиссий одновременно. 

#### Permission

Конкретные права действия для одного действия. Например `post.read`. 
Пермиссии могут назначаться как роли, так и конкретному юзеру.

## Схема архитектуры:

Схематично архитектуру можно разделить на 3 составные части: идентификация 
пользователя (поиск его по системе и сопоставление с искомым значением), 
аутентифкация (установление личности, кто он) и авторизация (какими правами 
обладает, куда доступ можно дать).

```
Security/
├── Identification/
│
├── Authentication/
│   ├── Guards/
│   ├── Sessions/
│   └── Tokens/
│
└── Authorization/
    ├── Gate/
    ├── Policy/
    ├── Role/
    └── Permission/
```

### Схема БД:

| Имя таблицы             | Предназначение                                |
|-------------------------|-----------------------------------------------|
| users                   | Таблица всех юзеров и админов                 |
| roles                   | Здесь находятся роли, базово `admin`, `user`  |
| role_translations       | Для бейджиков на сайте                        |
| permissions             | Здесь список прав (скоупы) и полномочий       |
| permission_translations | Для бейджиков на сайте                        |
| role_permissions        | Пивот-синхронизация ролей с правами           |
| user_roles              | Пивот-синхронизация юзеров с ролями           |
| user_permissions        | Пивот-синхронизация юзеров с правами          |
| password_resets         | Здесь хранятся временные токены ресета пароля |
| sessions                | Здесь хранятся сессии вместо PHP-функций      |

### Identification

Процесс узнавания пользователя, что он это вообще он, а не кто-то другой. 

```
Identification/
├── Identifier.php              # value object: тип + значение (email:foo@bar, id:42, phone:+380...)
├── IdentityResolver.php        # контракт: resolve(Identifier): ?User
├── Resolvers/
│   ├── EmailResolver.php
│   ├── PhoneResolver.php
│   ├── IdResolver.php          # для сессии и токена
├── IdentityNormilizer.php
└── IdentityManager.php         # цепочка резолверов, нормализация (trim, lowercase, E.164)
```
