# Neo — Declarative Schema Synchronization

**Статус:** Архитектурная спецификация  
**Компонент:** Database / Schema  
**Концепция:** Декларативное управление структурой БД

## 1. Философия

Миграция представляет собой декларацию желаемого состояния таблицы, а не историческую инструкцию изменения структуры.

Разработчик поддерживает один актуальный файл миграции на протяжении жизненного цикла таблицы.

При изменении декларации Neo самостоятельно определяет разницу между предыдущей и текущей структурой БД и формирует необходимые SQL-операции.

Цель — отказаться от бесконечного накопления отдельных миграций для каждого изменения структуры таблиц.

## 2. Объявление миграции

Пример:

```php
<?php

class CreatePostsTable extends Migration
{
    public function table()
    {
        Schema::create('posts', function (Blueprint $table) {
            $table->id();
            $table->string('title');
            $table->text('content');
            $table->timestamps();
        });
    }
}
```

При последующем изменении структуры разработчик редактирует этот же файл:

```php
<?php

class CreatePostsTable extends Migration
{
    public function table()
    {
        Schema::create('posts', function (Blueprint $table) {
            $table->id();
            $table->string('title');
            $table->text('content');
            $table->string('slug')->unique();
            $table->timestamps();
        });
    }
}
```

Версионирование через `$version` не требуется.

## 3. Обнаружение изменений

Neo использует хеширование файлов миграций.

При запуске соответствующей консольной команды:

1. Вычисляется хеш файла миграции.
2. Получается сохранённый хеш из БД.
3. Хеши сравниваются.
4. При совпадении миграция пропускается.
5. При несовпадении запускается процедура синхронизации схемы.

Для хеширования можно использовать SHA-256.

Проверка выполняется только при вызове соответствующей консольной команды, поэтому постоянный мониторинг файлов не требуется.

## 4. Архитектура синхронизации

Компоненты:

| Компонент | Ответственность |
|---|---|
| Migration | Объявление желаемой структуры |
| MigrationDetector | Обнаружение изменений файлов |
| SchemaSnapshot | Хранение предыдущего состояния схемы |
| SchemaComparator | Сравнение предыдущей и новой структур |
| SchemaDiff | Представление обнаруженных различий |
| SchemaMigrator | Применение изменений |
| SchemaBuilder | Генерация SQL-операций |

Общий процесс:

```text
Console Command
      |
      v
MigrationDetector
      |
      v
File Hash Comparison
      |
      v
Schema Declaration
      |
      v
SchemaComparator
      |
      v
SchemaDiff
      |
      v
SchemaBuilder
      |
      v
Database
      |
      v
Update Schema History
```

## 5. Хранение истории в БД

История изменений хранится непосредственно в базе данных, а не в локальных файлах.

Предлагаемая таблица `neo_schema_history`:

| Поле | Назначение |
|---|---|
| id | Идентификатор записи |
| migration | Имя миграции |
| file_hash | Последний применённый хеш файла |
| schema_snapshot | Сохранённое состояние схемы |
| applied_at | Время последней синхронизации |

История позволяет хранить предыдущие состояния схемы и использовать их при последующих сравнениях.

## 6. Schema Diff

Сравниваются два состояния:

- Предыдущее состояние схемы.
- Новое состояние, полученное из декларации миграции.

Schema Diff должен определять:

- Добавление столбцов.
- Удаление столбцов.
- Изменение типов столбцов.
- Изменение параметров столбцов.
- Добавление индексов.
- Удаление индексов.
- Изменение ограничений.
- Изменение других поддерживаемых характеристик таблицы.

Пример:

**Предыдущая структура:**

```sql
CREATE TABLE posts (
    id BIGINT PRIMARY KEY,
    title VARCHAR(255),
    content TEXT
);
```

**Новая структура:**

```sql
CREATE TABLE posts (
    id BIGINT PRIMARY KEY,
    title VARCHAR(255),
    content TEXT,
    slug VARCHAR(255) UNIQUE
);
```

**Результат Schema Diff:**

```sql
ALTER TABLE posts
ADD COLUMN slug VARCHAR(255) UNIQUE;
```

Если файл изменился, а структура осталась прежней, Schema Diff возвращает пустой результат.

## 7. Принципы работы

1. Один файл миграции представляет актуальную декларацию таблицы.
2. Версионирование миграций не используется.
3. Изменения файлов обнаруживаются через хеширование.
4. История предыдущих состояний хранится в БД.
5. SQL-операции генерируются автоматически на основании Schema Diff.
6. Неизменённые структуры не затрагиваются.
7. История изменений не требует создания дополнительных файлов миграций.

## 8. Важные архитектурные требования

### 8.1. Сохранность данных

Изменение структуры не должно приводить к непреднамеренной потере данных.

Удаление столбцов и преобразование несовместимых типов требуют отдельной политики обработки данных.

### 8.2. Транзакционность

По возможности применение изменений должно выполняться транзакционно.

Необходимо учитывать различия транзакционной поддержки DDL между СУБД.

### 8.3. Идемпотентность

Повторный запуск синхронизации при отсутствии изменений не должен порождать дополнительных операций.

### 8.4. Разделение хеширования и сравнения схем

Изменение файла не обязательно означает изменение структуры БД.

Хеш используется исключительно для обнаружения изменений декларации. Фактическое решение о необходимости SQL-операций принимает SchemaComparator.

### 8.5. Управление историей

Предыдущие снимки схемы должны сохраняться независимо от актуального состояния, чтобы обеспечивать возможность анализа истории изменений.

## 9. Итоговая концепция

Neo использует декларативный подход к управлению структурой БД.

Разработчик описывает желаемое состояние таблицы в одном файле. Neo обнаруживает изменения декларации, сравнивает новое состояние с предыдущим, формирует Schema Diff и автоматически синхронизирует структуру базы данных.

**Миграция становится декларацией состояния, а история изменений — внутренним механизмом самого Neo.**
